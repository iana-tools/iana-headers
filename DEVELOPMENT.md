# Development Notes

## Database

`db/<registry>.rec` holds one record per IANA entry:

```
Tag: 18
Words: cose single signer data object
Semantics: COSE Single Signer Data Object
Reference: [RFC9052]
Source: heuristic
```

- `Tag` is the registry key (an integer, a CoAP code such as `2.05`, `<signaling code>.<option number>` such as `7.01.2`, or an HTTP field name).
- `Words` are lowercase tokens; the generator applies the C style (`CBOR_TAG_COSE_SINGLE_SIGNER_DATA_OBJECT`).
- `Source` says where `Words` came from: `heuristic` / `llm` (generated by `name.py`), `manual` (decided by a human; wins over everything), `new` / `needs-manual` (not named yet: `make check` fails until a human decides), `skip` (deliberately left out of the headers; keeps `make sync` from re-adding it).
- `Semantics` and `Reference` are copied from IANA and are what `sync` compares against; new CBOR tag records also preserve IANA's `Data Item` field separately for review. A `#` line may precede a record to explain an override. `Note` can record why an entry was skipped during interactive review.
- `Lifecycle` records explicit IANA states such as `provisional`, `temporary`, or `under-review`. `Review: monitor` means the entry is still in that state; `Review: pending` blocks `make check`/generation until the IANA change is reviewed; sync stores IANA's new text in `IANA Semantics` next to the committed `Semantics`, and `make review` resolves it (see below).
- `IANA Semantics` is IANA's current wording when it differs from the committed `Semantics`. For a stable entry it is informational (the name stays; copy the text into `Semantics` and delete `IANA Semantics` if the header comment should follow IANA). Sync reports each wording change once.
- `Namespace` puts the entry in a family from `db/namespaces/<registry>.rec` (see "CBOR tag namespaces"); its `Words` must start with the family's prefix.
- `Previous Words` documents an intended rename of an already-published name (see "Published names" below).
- `Suggested Words` / `Suggested By` are written by `make name` and `make review` on every name they save: what the namer (`heuristic` or `llm`) proposed, or `(none)`. `Words` equal to `Suggested Words` means the suggestion was accepted; anything else is a human override. `python3 c/name.py --review-stats` reports the acceptance rate and lists the overrides, which are the cases to learn new heuristic rules from.

Naming rules differ per registry (`NAMERS` in `c/name.py`), because the identifiers published before the database existed were derived from different columns:
CoAP codes are prefixed with their class (`COAP_CODE_CLIENT_ERROR_NOT_FOUND`), HTTP field names come from the field name itself, CoAP content formats fold media type parameters into the name.
Changing a rule only affects entries that are not in `db/` yet.

For a new IANA registration, `make sync review` shows each pending entry's Data Item, Semantics, Reference, and lifecycle state, then numbered name suggestions with the C identifier each would produce (e.g. `CBOR_TAG_CORIM_MAP`). For CBOR tags the suggestions are the heuristic name, a name taken from the Data Item when it reads like one (`Proof of Process Packet (PPPP)`), and the unshortened Semantics. Suggestions that collide are listed but cannot be picked; long ones are flagged. Committed names with similar Semantics are shown so related registrations (`suit …`, `ur …`) stay consistent. Pick a suggestion by number (`a` takes the first), type a name in any case or punctuation (`e`; it is stored as lowercase words), or skip with a reason recorded in `Note`. Accepting or editing a name saves it as `Source: manual`. Quit at any point and rerun `make review` to continue; choices made so far are saved. `make check` and `make generate` remain the final validation gates.

`make name` leaves a name to review (`Source: needs-manual`) when the result would have more than 10 words not counting numbers (OIDs, versions), i.e. the description is a sentence rather than a name; for CBOR tags a Data Item that reads like a name is used instead when there is one. `c/test_name.py` pins the heuristic's output for the tags added by the `2026-10-08` snapshot; update that table when a rule change is intended.

When `name` reports a collision in non-interactive mode, give the entries distinct `Words` and set `Source: manual`. Names only have to be unique inside one generated enum (signaling option numbers get one enum per CoAP code).

When the migration to the database was made, the headers regenerated from `db/` were identical to the ones published by the previous csv-driven generators.

## Experimental semantic namer

`c/experimental_namer.py` is a standalone CBOR-tag experiment; it does not modify `db/` or generated headers. Its TF-IDF nearest-neighbour baseline builds a vector space from existing `Semantics` and predicts `Words` by weighted voting over similar records. This is local corpus-based ML, not an LLM; its output vocabulary is limited to words already used in existing names. An optional `--llm` comparison queries an OpenAI-compatible local llama.cpp server and supplies few-shot examples from the same annotated namespace and nearest semantic matches. A separate hand-curated sidecar, `c/experiments/cbor_tag_name_parts.rec`, tests decomposing names into `Namespace` and `Label` without changing production records. The sidecar is an annotation experiment, not a prediction-accuracy dataset: labels intentionally compose to the already committed `Words` for those sample tags.

Run a leave-one-out comparison against the current heuristic:

```sh
python3 c/experimental_namer.py --evaluate
```

Inspect one held-out example or suggest names for newly synced records without writing changes:

```sh
python3 c/experimental_namer.py --tag 18
python3 c/experimental_namer.py --tag 107 --llm
python3 c/experimental_namer.py --tag 107 --llm --compare-xml
python3 c/experimental_namer.py --tag 1070 --llm
python3 c/experimental_namer.py --tag 107 --llm --temperature 0.7
python3 c/experimental_namer.py --suggest-new
```

`--compare-xml` uses the archived CBOR tags XML and compares LLM suggestions from XML `Semantics` alone versus separately labeled `Tag`, `Description`, `Semantics`, and `Reference` fields. Treat these outputs as experiments: the nearest-neighbour model can only reuse existing name tokens and may perform worse than the hand-tuned naming rules; XML field separation does not guarantee a better LLM suggestion.

The leave-one-out evaluation excludes each target record from its own training set.

Lifecycle-aware sync preserves existing `Semantics` and `Words`. If IANA changes the description of a record with a `Lifecycle` marker, sync sets `Review: pending` and saves the new text as `IANA Semantics`; `make check` then blocks generation until the record is reconciled. `make review` shows the committed and the new IANA text, the lifecycle transition (e.g. `temporary -> stable`) and, when the new text names the entry differently, a rename suggestion. Keeping or renaming copies the new text into `Semantics`, removes `IANA Semantics`, and sets `Lifecycle`/`Review` to `<state>`/`monitor` while IANA still marks the entry, or `stable`/`resolved` once it does not. `[l]ater` leaves the record pending. Renaming a published identifier is a breaking change for users of the header; it is offered here because provisional and temporary registrations are expected to change.

## CBOR tag namespaces

`db/namespaces/cbor_tags.rec` lists the families of CBOR tags that share a name prefix, one record each: `Namespace`, `Prefix`, `Organization`, `Description`, `Spec`, and a `Semantics Match` and/or `Reference Match` regular expression that recognises the family's tags from their IANA fields. A named group `label` captures the item's own name from the IANA text (`^ur:(?P<label>[a-z0-9-]+)` gives `seed` for `ur:seed, Cryptographic seed`).

| Namespace | Organization | Recognised by | Tags |
| --- | --- | --- | --- |
| `ur` | Blockchain Commons (Uniform Resources) | `ur:<type>` | 49 |
| `platformv` | PlatformV | `PlatformV_<NAME>` | 13 |
| `cose` | IETF COSE | `COSE ...` | 8 |
| `yang` | IETF CORE (RFC 9254) | `YANG ...` | 5 |
| `moat` | MoaT | `MoaT ...` | 3 |
| `suit` | IETF SUIT | `SUIT_<Name>` | 2 (+3 in the next sync) |

- `sync` sets `Namespace` on new records that a rule matches.
- `make name` (and the v2 rules) start the name with the prefix and never repeat it (`cose cose key` → `cose key`). Where the text alone gives no usable name, a captured label is used: a `ur:` tag with a long description is still named `ur <type>`.
- `make check` fails if a matching record lacks `Namespace`, names an unknown one, matches two, or has `Words` without the prefix.
- After adding or changing a namespace, run `make namespaces` (`DRY_RUN=1` to preview) to assign existing records, then review the result like any other db change.

The generated CBOR tag enum starts with a comment that explains every abbreviation its names use (`c/glossary.py`): each namespace prefix with its description, organisation and spec link (`UR  Uniform Resources … (Blockchain Commons)`), acronyms whose expansion IANA gives (`CWT  CBOR Web Token`), and word shortenings from the naming rules (`STRCT  structure`). A shortening is listed only where the entry's own IANA text contains the full word, and only abbreviations that occur in the names are listed.

Naming rule: spell words out, except a scheme's own name or an acronym that IANA or the spec uses (UR, COSE, CWT, SUIT, IRI). Those are names, not abbreviations: `UNIFORM_RESOURCE_SEED` would hide the term people see in the data (`ur:seed/…`). The glossary explains them instead.

Families without a recognised name scheme (one author's assorted tags, or self-describing names such as the RFC 8746 typed arrays) deliberately have no namespace. `c/experiments/cbor_tag_name_parts.rec` predates this table; only `c/experimental_namer.py` still reads it.

## CBOR tag names v2 (proposal)

Many v1 CBOR tag names read like sentences (`HINT_THAT_INDICATES_AN_ADD_LVL_OF_INDIRECTION`), repeat themselves (`UR_SEED_CRYPTOGRAPHIC_SEED`) or abbreviate inconsistently, because the registry has no name column and the v1 heuristic paraphrases the description. The plan is a v2 name for every tag, with the v1 names that change kept as deprecated duplicates until v3.

Step 1 (`c/cbor_names_v2.py`, preview with `make names-v2`) derives names from the IANA fields only: the `ur:` type; an acronym that IANA gives in parentheses (`CBOR Web Token (CWT)` → `CWT`); otherwise a short noun phrase from Semantics without citations, sentence frames ("A CBOR tag that contains", "indicates that") and trailing clauses; for text that is still a sentence, a unique reference URL name (`…/quoted` → `QUOTED`) or a name-like Data Item. Full words except `id`, `ref`, `config`, `info`. Dropped detail is put back only where two names would collide (`EXPECTED_BASE16` vs `EXPECTED_BASE16_LOWERCASE`); spec pointers ("see Section …") never are. A human (`Source: manual`) name stands where the rules collide. Nothing in `db/` or the headers changes yet.

Step 2 (planned) takes spec names that IANA does not state, such as `COSE_SIGN1` for tag 18, from the referenced RFCs' CDDL (`COSE_Sign1_Tagged = #6.18(...)`).

## IANA updates

Everything runs from the Makefile; GitHub is optional. `make refresh` is one complete update: it keeps a copy of `db/`, runs `sync` into a new `iana/snapshots/<date>/` directory and `name`, and then either discards the snapshot (IANA brought nothing new) or prints a Markdown review summary compared against the saved copy (`SUMMARY=<file>` writes it to a file instead; the file is removed when nothing changed). Git is not needed for this.

To finish an update, wherever it came from:

1. Resolve **Needs a decision**: names that could not be generated and IANA lifecycle changes, with `make review` or by editing `db/*.rec`.
2. Read **New names**. To change one, edit its `Words` and set `Source: manual`. `make check` rejects a `heuristic`/`llm` record whose `Words` no longer match `Suggested Words`, so a hand edit is always recorded as a human decision.
3. Run `make ci BASE=<branch it goes into>` (tests, `check`, the published-name guard below, `verify`), then commit `db/` and the snapshot together. Each reviewer change becomes data for `make review-stats`.

### With GitHub

`.github/workflows/iana-sync.yml` runs `make refresh` every Monday and on demand (Actions → IANA Sync → Run workflow) and opens a pull request from the `iana-sync` branch with the summary as its description. While that pull request is open, later runs do nothing, so they never overwrite a reviewer's edits on the branch. `.github/workflows/python-test.yml` runs the same targets as `make ci` on every pull request and puts the report on the run's summary page.

Repository setup: enable *Settings → Actions → General → Allow GitHub Actions to create and approve pull requests*. With the default `GITHUB_TOKEN`, GitHub does not run CI on pull requests created by a workflow; add a fine-grained token with contents and pull-request write access as the `IANA_SYNC_TOKEN` secret to get CI on sync pull requests (or close and reopen the pull request to trigger it).

### Without GitHub

Run `make refresh` by hand, from cron, or from another CI system, and review the result however the project reviews changes (a branch, a merge request, a patch by email). For example, a weekly cron job that leaves a branch for a maintainer:

```sh
cd /path/to/iana-headers && git switch -c iana-sync-$(date -u +%F) &&
make refresh SUMMARY=/tmp/iana-update.md && test -f /tmp/iana-update.md &&
git add db iana/snapshots && git commit -m "IANA sync $(date -u +%F)" -m "$(cat /tmp/iana-update.md)"
```

GitLab CI or similar can do the same with its own merge-request step: call `make refresh` on a schedule, and `make ci BASE=origin/main` on merge requests. Without git, keep a copy of the published `db/` and compare against it: `make report BASE_DIR=../db-published` and `make ci BASE_DIR=../db-published`.

Only two things refer to GitHub: the `c/src` submodule URL (`git@github.com:iana-tools/iana-headers-c.git`, which needs a GitHub SSH key to clone; generation does not need the submodule, it creates the headers if they are missing) and the source link written into a new header's preamble.

## Published names

The headers published from `db/` (the `c/src` submodule, `iana-tools/iana-headers-c`) are used by other projects, so an identifier must not silently change. `make ci` (and CI on every pull request) runs `c/report.py --strict` against the target branch and fails if a published name of a stable entry is renamed, set to `skip`, or deleted. Renames of provisional/temporary registrations are listed but allowed. For an intended rename, add `Previous Words: <old words>` to the record (or a `Note` for a removal); the run's summary page shows the full report.

## IANA source snapshots

`c/cache/` is a mutable, ignored network cache. `make sync` saves the exact cached source files used by that run into a new root-level `iana/snapshots/YYYY-MM-DD/` directory, with a `README.md` manifest mapping each file to its IANA URL. These source snapshots sit alongside `db/` as tracked inputs: review and commit them with related database and generated-header changes. `make sync` does not stage or commit anything. Snapshots are immutable; if you need another sync on the same date, use `python3 c/sync.py --snapshot-dir iana/snapshots/YYYY-MM-DD-run2`.

`iana/snapshots/2026-10-08/` is the pinned parser-test fixture. `c/test_iana_snapshots.py` reads it offline, including the CoAP XML registries that intentionally fall back to CSV. Runtime cache files remain out of Git.

## Key Insights and Challenges

### CBOR Semantic Tags Naming Heuristic
- The CBOR semantic tags don't always have a clear name provided by submitters.
- Implemented a heuristic to generate names based on the semantic description field from the IANA CBOR tag registry.
    - Ignored content inside brackets like `Binary UUID ([RFC4122, Section 4.1.2])`, rendered as `CBOR_TAG_37_BINARY_UUID`.
    - Ignored sentences that reference other standards via `define in` key phrases, such as `A collection of NCMS metadata elements. The key value pairs of the map are defined in AdatP-5636.4`, rendered as `CBOR_TAG_42602_A_COLLECTION_OF_NCMS_METADATA_ELEMENTS`.

### Handling CoAP Signalling Option Numbers
- CoAP signalling option numbers can apply to multiple CoAP codes, requiring special handling.
- Unable to generate a single enum list for the IANA registry table due to this complexity.

### CoAP Content Format Handling
- CoAP content format is based on MIME types and requires handling of special characters like `+` and `/`.
- Additional parameter fields need to be factored in.
- Special handling of certain parameters to avoid repeated words.
    - For example, `application/cose; cose-type="cose-encrypt0"; Ref: [RFC9052]` should be rendered as `COAP_CONTENT_FORMAT_APPLICATION_COSE_ENCRYPT0`.

## Code Style Justification

### Use of Screaming Snake Case
- Typedef enums and other macro constants use screaming snake case for readability.
- Easier for non-English speakers to read compared to camel case.
    - Supporting sources: In "460: I Don’t Care What Your Math Says," one of the speakers highlighted the difficulties of reading camel case for non-English speakers ([Transcript](https://embedded.fm/transcripts/460)).

## Project Structure Justification

### Arrangement by Language Family
- Project folder structure is organized in terms of language family rather than protocol.
- Better reflects the likelihood of a project using one language and toolset while potentially utilizing multiple protocols.
