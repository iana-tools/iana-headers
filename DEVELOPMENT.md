# Development Notes

## Database

`db/<registry>.rec` holds one record per IANA entry:

```
Tag: 18
Words: cose single signer data object
Semantics: COSE Single Signer Data Object
Reference: [RFC9052]
Source: heuristic
```

- `Tag` is the registry key (an integer, a CoAP code such as `2.05`, `<signaling code>.<option number>` such as `7.01.2`, or an HTTP field name).
- `Words` are lowercase tokens; the generator applies the C style (`CBOR_TAG_COSE_SINGLE_SIGNER_DATA_OBJECT`).
- `Source` says where `Words` came from: `heuristic` / `llm` (generated by `name.py`), `manual` (decided by a human; wins over everything), `new` / `needs-manual` (not named yet: `make check` fails until a human decides), `skip` (deliberately left out of the headers; keeps `make sync` from re-adding it).
- `Semantics` and `Reference` are copied from IANA and are what `sync` compares against; new CBOR tag records also preserve IANA's `Data Item` field separately for review. A `#` line may precede a record to explain an override. `Note` can record why an entry was skipped during interactive review.
- `Lifecycle` records explicit IANA states such as `provisional`, `temporary`, or `under-review`. `Review: monitor` means the entry is still in that state; `Review: pending` blocks `make check`/generation until the IANA change is reviewed. After confirming a transition to stable, update the IANA fields and `Words`, then set `Lifecycle: stable` and `Review: resolved` (or remove the lifecycle fields).

Naming rules differ per registry (`NAMERS` in `c/name.py`), because the identifiers published before the database existed were derived from different columns:
CoAP codes are prefixed with their class (`COAP_CODE_CLIENT_ERROR_NOT_FOUND`), HTTP field names come from the field name itself, CoAP content formats fold media type parameters into the name.
Changing a rule only affects entries that are not in `db/` yet.

For a new IANA registration, `make sync review` shows each pending entry's Data Item, Semantics, Reference, and lifecycle state, then numbered name suggestions with the C identifier each would produce (e.g. `CBOR_TAG_CORIM_MAP`). For CBOR tags the suggestions are the heuristic name, a name taken from the Data Item when it reads like one (`Proof of Process Packet (PPPP)`), and the unshortened Semantics. Suggestions that collide are listed but cannot be picked; long ones are flagged. Committed names with similar Semantics are shown so related registrations (`suit …`, `ur …`) stay consistent. Pick a suggestion by number (`a` takes the first), type a name in any case or punctuation (`e`; it is stored as lowercase words), or skip with a reason recorded in `Note`. Accepting or editing a name saves it as `Source: manual`. Quit at any point and rerun `make review` to continue; choices made so far are saved. `make check` and `make generate` remain the final validation gates.

The CBOR tag heuristic leaves a name to review (`Source: needs-manual`) when the result would be longer than 10 words, i.e. the Semantics is a sentence rather than a name, unless the Data Item reads like a name. `c/test_name.py` pins the heuristic's output for the tags added by the `2026-10-08` snapshot; update that table when a rule change is intended.

When `name` reports a collision in non-interactive mode, give the entries distinct `Words` and set `Source: manual`. Names only have to be unique inside one generated enum (signaling option numbers get one enum per CoAP code).

When the migration to the database was made, the headers regenerated from `db/` were identical to the ones published by the previous csv-driven generators.

## Experimental semantic namer

`c/experimental_namer.py` is a standalone CBOR-tag experiment; it does not modify `db/` or generated headers. Its TF-IDF nearest-neighbour baseline builds a vector space from existing `Semantics` and predicts `Words` by weighted voting over similar records. This is local corpus-based ML, not an LLM; its output vocabulary is limited to words already used in existing names. An optional `--llm` comparison queries an OpenAI-compatible local llama.cpp server and supplies few-shot examples from the same annotated namespace and nearest semantic matches. A separate hand-curated sidecar, `c/experiments/cbor_tag_name_parts.rec`, tests decomposing names into `Namespace` and `Label` without changing production records. The sidecar is an annotation experiment, not a prediction-accuracy dataset: labels intentionally compose to the already committed `Words` for those sample tags.

Run a leave-one-out comparison against the current heuristic:

```sh
python3 c/experimental_namer.py --evaluate
```

Inspect one held-out example or suggest names for newly synced records without writing changes:

```sh
python3 c/experimental_namer.py --tag 18
python3 c/experimental_namer.py --tag 107 --llm
python3 c/experimental_namer.py --tag 107 --llm --compare-xml
python3 c/experimental_namer.py --tag 1070 --llm
python3 c/experimental_namer.py --tag 107 --llm --temperature 0.7
python3 c/experimental_namer.py --suggest-new
```

`--compare-xml` uses the archived CBOR tags XML and compares LLM suggestions from XML `Semantics` alone versus separately labeled `Tag`, `Description`, `Semantics`, and `Reference` fields. Treat these outputs as experiments: the nearest-neighbour model can only reuse existing name tokens and may perform worse than the hand-tuned naming rules; XML field separation does not guarantee a better LLM suggestion.

The leave-one-out evaluation excludes each target record from its own training set.

Lifecycle-aware sync preserves existing `Semantics` and `Words`. If IANA changes the description of a record with a `Lifecycle` marker, sync sets `Review: pending`; `make check` then blocks generation until the record is reconciled.

## IANA source snapshots

`c/cache/` is a mutable, ignored network cache. `make sync` saves the exact cached source files used by that run into a new root-level `iana/snapshots/YYYY-MM-DD/` directory, with a `README.md` manifest mapping each file to its IANA URL. These source snapshots sit alongside `db/` as tracked inputs: review and commit them with related database and generated-header changes. `make sync` does not stage or commit anything. Snapshots are immutable; if you need another sync on the same date, use `python3 c/sync.py --snapshot-dir iana/snapshots/YYYY-MM-DD-run2`.

`iana/snapshots/2026-10-08/` is the pinned parser-test fixture. `c/test_iana_snapshots.py` reads it offline, including the CoAP XML registries that intentionally fall back to CSV. Runtime cache files remain out of Git.

## Key Insights and Challenges

### CBOR Semantic Tags Naming Heuristic
- The CBOR semantic tags don't always have a clear name provided by submitters.
- Implemented a heuristic to generate names based on the semantic description field from the IANA CBOR tag registry.
    - Ignored content inside brackets like `Binary UUID ([RFC4122, Section 4.1.2])`, rendered as `CBOR_TAG_37_BINARY_UUID`.
    - Ignored sentences that reference other standards via `define in` key phrases, such as `A collection of NCMS metadata elements. The key value pairs of the map are defined in AdatP-5636.4`, rendered as `CBOR_TAG_42602_A_COLLECTION_OF_NCMS_METADATA_ELEMENTS`.

### Handling CoAP Signalling Option Numbers
- CoAP signalling option numbers can apply to multiple CoAP codes, requiring special handling.
- Unable to generate a single enum list for the IANA registry table due to this complexity.

### CoAP Content Format Handling
- CoAP content format is based on MIME types and requires handling of special characters like `+` and `/`.
- Additional parameter fields need to be factored in.
- Special handling of certain parameters to avoid repeated words.
    - For example, `application/cose; cose-type="cose-encrypt0"; Ref: [RFC9052]` should be rendered as `COAP_CONTENT_FORMAT_APPLICATION_COSE_ENCRYPT0`.

## Code Style Justification

### Use of Screaming Snake Case
- Typedef enums and other macro constants use screaming snake case for readability.
- Easier for non-English speakers to read compared to camel case.
    - Supporting sources: In "460: I Don’t Care What Your Math Says," one of the speakers highlighted the difficulties of reading camel case for non-English speakers ([Transcript](https://embedded.fm/transcripts/460)).

## Project Structure Justification

### Arrangement by Language Family
- Project folder structure is organized in terms of language family rather than protocol.
- Better reflects the likelihood of a project using one language and toolset while potentially utilizing multiple protocols.
